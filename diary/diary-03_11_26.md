Working-state prediction before scaling experiment (seeds 3662–3664): use an
ordinary fixed route over contributor-defined state/event types and fixed-size
immutable payloads. Compare a state-threading process cursor to explicitly
threading execute results, alternating measurement order across seeds. At
100, 1,000 and 10,000 events, predict identical final states and accounting,
exactly n invocations and 2n+1 workspace messages, and approximately linear total
runtime. Report mean and sample standard deviation over three seeds; do not
claim constant memory or time-independent risk. Use the reusable
benchmarks/state_stream.py harness. Profile the largest process run before
considering numerical optimization. This tests working-state scheduling, not
persistence, adversarial containment, learning or a general streaming planner.

Measured working-state result (seeds 3662–3664): all final states, invocation
counts, costs and ledger charges matched direct execution at every size.
Workspace messages were exactly 201, 2,001 and 20,001. Mean ± sample standard
deviation of process seconds: 0.000526 ± 0.000027; 0.004960 ± 0.000163;
0.067479 ± 0.001206. Direct baseline seconds: 0.000601 ± 0.000247;
0.008764 ± 0.007141; 0.059211 ± 0.011557. The largest process run was about
14% slower than the baseline mean. Process time per event was approximately
5.26, 4.96 and 6.75 microseconds: broadly linear over this range, with increased
per-event cost at the largest size. This does not establish asymptotic constant
transition cost; the small baseline had substantial timing variance. Exact
state/accounting and linear history predictions held; runtime scaling is only
approximately supported over the measured range. There is no memory compression
or speedup claim.

The profiled largest run took 0.156 s including profiling overhead. Process.step
accounted for 0.146 s cumulatively, execute 0.139 s, recursive route evaluation
0.087 s, runtime type checks 0.034 s and ledger accounting 0.015 s. No dominant
numerical kernel justified Elisa work. Permanent tests check failure-prefix
preservation, event signatures, repeated input types, lazy cancellation, bounded
consumption, shared nested-request budgets and risk, and reentrant refusal.
Inspection also found negative invocation budgets bypassed execute's zero check;
execute now rejects negative/nonintegral invocation budgets and negative/nonfinite
cost budgets before posting messages. This is input validation, not containment
of arbitrary Python experts. Lean proves conditional immutable-state invariants
and cursor preservation on failure; neither proves payload immutability or effect
rollback. Full state/effects, durable memory and continual-learning gaps remain
open.

the exact logical-byte limit; denied writes make no record. Predict mean lookup

than 10× the mean query time. Report mean and sample standard deviation for

are tested separately, not represented by this independent-record workload.

Measured durable-memory results (seeds 3668–3670): all 9,000 sampled recalls
across three sizes and three seeds matched their full original typed records
after closing/reopening. Each database filled its exact logical capacity;
duplicates stayed idempotent and fresh records were refused when full. An
ungranted append was refused before populating each database. The final backend
explicitly requires file-backed WAL mode and FULL synchronous commits; an
in-memory database is refused. This does not prove power-loss recovery or the
honesty of the underlying filesystem. The local SQLite default synchronous mode
was already FULL; setting it explicitly avoids depending on a platform default.
